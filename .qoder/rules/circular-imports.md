# Правила исправления циклических импортов

## Общие принципы:
1. **Всегда проверяй актуальность кода** - если файл выглядит подозрительно, сначала убедись, что он используется в проекте
2. Используй `grep_code` или `search_codebase` чтобы найти все импорты подозрительного модуля
3. Если модуль нигде не импортируется - это кандидат на удаление

## Алгоритм проверки устаревшего кода:

### 1. Проверка использования модуля:
```bash
# Найти все импорты модуля
grep_code "from\s+path\.to\.module|import\s+.*module_name"

# Найти упоминания имени модуля
grep_code "module_name"
```

### 2. Признаки устаревшего кода:
- Модуль не импортируется нигде в проекте
- Содержит много закомментированного кода
- Импортирует несуществующие модули или функции
- Тесты пытаются импортировать несуществующие функции/классы
- Функции не экспортируются из модуля (нет в `__all__` или не используются)

### 3. Безопасное удаление:
- Сначала убедись, что модуль действительно не используется
- Удали файл с помощью `delete_file`
- Закоммить удаление с подробным объяснением
- Проверить, что pre-commit проходит без ошибок

## Исправление архитектурных нарушений:

### 1. Анализ циклических импортов:
- Изучи вывод import-linter
- Найди модули, которые создают циклы
- Определи, какие импорты можно переместить или удалить

### 2. Стратегии исправления:
1. **Удаление неиспользуемых модулей** (приоритет #1)
2. **Перемещение общих классов/функций в отдельные модули**
3. **Использование lazy imports** (импорт внутри функции)
4. **Разделение больших модулей на более мелкие**
5. **Создание абстракций для разрыва циклов**

### 3. Правила по слоям архитектуры:
- `app.core` не должен импортировать `app.modules`
- `app.utils` не должен импортировать `app.modules`
- `app.modules` не должен импортировать `app.client_bot`
- `app.admin_bot` не должен импортировать `app.utils` или `app.client_bot`

## Примеры работы:

### Проверка подозрительного файла:
```python
# 1. Найти все импорты файла
grep_code "from\s+app\.path\.to\.suspicious_module"

# 2. Если ничего не найдено - проверить по имени
grep_code "suspicious_module_name"

# 3. Если только комментарии - кандидат на удаление
```

### Типичные паттерны устаревшего кода:
- Тесты импортируют `from module import NonExistentClass`
- Модули содержат только закомментированный код
- Импорты указывают на несуществующие файлы
- В коде есть TODO и FIXME без реализации

## Коммиты:
- Группируй удаление связанных устаревших файлов в один коммит
- Объясняй в сообщении коммита, почему файл удален
- Указывай, какие архитектурные нарушения это исправляет
- Отмечай уменьшение количества зависимостей

## Проверки после изменений:
1. Запусти `pre-commit run --all-files`
2. Убедись, что количество архитектурных нарушений уменьшилось
3. Проверь, что важная функциональность не сломалась
4. Все тесты должны проходить
