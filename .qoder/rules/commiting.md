# Правила работы с Git и анализа кода

## Git правила:
1. **НИКОГДА не используй `git reset --hard`** - это удаляет все изменения без возможности восстановления
2. Используй `git reset --mixed` или `git reset --soft` для отмены коммитов
3. Всегда проверяй что именно коммитишь с помощью `git diff` перед коммитом
4. Разделяй логические изменения и форматирование на разные коммиты

## Работа с терминалом и pager:
1. Если вижу `:` или `(END)` в терминале - это git pager (less), нужно нажать `q` для выхода
2. Для избежания pager используй `git --no-pager diff` или `git --no-pager log`
3. Если команда "зависла" с `:...skipping...` - это pager, не паникуй
4. Всегда проверяй завершилась ли команда по появлению нового prompt `$`

## Анализ изменений:
1. Сначала исключи служебные файлы: `grep -v "\.qoder" | grep -v "\.vscode"`
2. Отдели логические изменения от форматирования
3. Проверяй ключевые файлы на предмет важных изменений перед коммитом
4. Используй `git --no-pager diff --stat` для обзора изменений
5. **ОБЯЗАТЕЛЬНО проверяй каждое изменение на смысл и спрашивай у пользователя о неочевидных изменениях**
6. **Не коммить неиспользуемые импорты или код** - всегда проверяй, что добавляемый код действительно нужен

## Детальная проверка кода ПЕРЕД коммитом:
1. **Каждый добавленный импорт** - используется ли он в файле?
2. **Каждая новая переменная** - где и как используется?
3. **Каждая новая функция/метод** - вызывается ли где-то?
4. **Странные изменения** - неожиданные значения, комментарии, TODO, странная логика
5. **Удаленный код** - почему удален, может ли это сломать что-то?
6. **Изменения в конфигурации** - понятна ли цель изменения?
7. **ЕСЛИ ЧТО-ТО ВЫГЛЯДИТ СТРАННО ИЛИ НЕЯСНО - ВСЕГДА СПРОСИ У ПОЛЬЗОВАТЕЛЯ**
8. **Лучше лишний раз переспросить, чем закоммитить ерунду**

## Проверка устаревшего кода:
1. **Подозрительные файлы** - если файл выглядит странно, проверь используется ли он
2. **Поиск импортов**: `grep_code "from\s+module\.path|import\s+.*module_name"`
3. **Поиск упоминаний**: `grep_code "module_name"`
4. **Если не найдено** - возможно файл устарел и не нужен

## Коммиты:
1. Группируй связанные изменения
2. Пиши осмысленные сообщения коммитов
3. Отдельно коммить: логику, форматирование, конфигурацию
4. **Перед коммитом логических изменений - уточни у пользователя цель каждого изменения**
5. **При малейших сомнениях - спрашивай у пользователя**

## Сообщения коммитов:
```
Тип: краткое описание (до 50 символов)

- Подробное описание что изменено
- Почему изменено
- Какие проблемы решает
- Влияние на архитектуру/зависимости
```

### Типы коммитов:
- `fix:` - исправление багов
- `feat:` - новая функциональность
- `refactor:` - рефакторинг кода
- `remove:` - удаление устаревшего кода
- `docs:` - документация
- `test:` - тесты
- `style:` - форматирование

## Работа с pre-commit:
1. Всегда запускай `pre-commit run --all-files` перед коммитом
2. Исправляй ошибки по одной
3. Каждое исправление - отдельный коммит
4. При проблемах с кэшем: `pre-commit clean`

## Главный принцип:
**"ЕСЛИ СОМНЕВАЕШЬСЯ - СПРАШИВАЙ!"**

## Алгоритм работы:
1. Проанализируй изменения
2. Проверь актуальность всех файлов
3. Убедись что код используется
4. Исправь проблемы по одной
5. Каждое исправление - коммит
6. При сомнениях - спроси пользователя
