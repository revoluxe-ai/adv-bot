# Tiriel OPSX: разрывы контрактов (ориентация)

Краткий список того, где новичок получит противоречивые указания. Только документация, frontmatter команд и индексы; репозиторий не менялся.

1. **Две «истины» графа пайплайна:** живой `.cursor/pipeline/GRAPH.md` (inventory 72, post-impl → `/opsx-plan-verification`, «never pyright») и замороженная копия `.opsx/upstream/a71601dba3b9/.cursor/pipeline/GRAPH.md` (inventory 35, post-impl → pyright/antipattern/static), плюс заглушка-описание в `mental-contracts/.cursor/pipeline/GRAPH.md` без самого графа.
2. **GRAPH устарел относительно диска:** в meta `evidence_note` заявлено, что split-APPLY команды «absent on disk», хотя есть `.cursor/commands/opsx-apply-design.md` и соседние `opsx-apply-*.md`.
3. **`openspec/config.yaml` vs адаптер:** в контексте config тесты/smoke «NOT_DECLARED_IN_TARGET_SNAPSHOT», тогда как `.opsx/adapters/vue-npm/README.md` и `.opsx/project/quality-gates.md` объявляют `frontend_tests`, `smoke_acceptance`, `backend_tests` как AVAILABLE.
4. **Post-apply маршрут:** GRAPH для `impl_done` ставит первым шагом `/opsx-plan-verification` → `/opsx-next-check` → `/opsx-verify`, а каноническое тело `.cursor/commands/opsx-apply.md` (секция «Post-apply next-step recommend») ведёт сразу на `/opsx-verify mode=impl` и WB-цепочку pyright/external-call без упоминания plan-verification.
5. **TARGET OVERRIDE vs встроенное canonical body:** frontmatter команд (например `.cursor/commands/opsx-apply.md`, `.cursor/commands/opsx-fix-bug.md`) запрещает Poetry/pytest/pyright, но ниже `BEGIN CANONICAL SOURCE BODY` остаются `poetry run pytest`, `/opsx-pyright-strict-coverage` и ссылки на `.cursor/rules/TESTING_RULES.mdc` / PG-session — политика WB, не game.
6. **Дублирующая test-policy в upstream:** `.opsx/upstream/a71601dba3b9/.cursor/rules/testing-rules.mdc` описывает Poetry/pytest/pyright для WB Sky, в то время как активная политика — `.cursor/rules/testing-rules.mdc` (vue-npm, `node --test`).
7. **Три разных «счётчика» команд:** на диске ~96 файлов `.cursor/commands/opsx*.md`, в `.opsx/registry/command_activation.ndjson` — 86 строк, в `.opsx/registry/fast_port_summary.json` — `installed_commands: 48`; newcomer не поймёт, что считать установленным.
8. **Параллельный индекс mental-contracts:** `mental-contracts/_meta/INDEX.json` указывает пути `mental-contracts/.cursor/commands/…` со статусом CANDIDATE, дублируя SoT `.cursor/commands/**` без явной пометки «не исполнять» в корне репо.
9. **Разные токены handoff при одном gate:** projectization fail-closed в `.cursor/commands/opsx.md` отдаёт `NEXT_ACTION: /opsx-projectize`, а в `.cursor/commands/opsx-pipeline.md` и большинстве worker-команд — `NEXT_COMMAND: /opsx-projectize` (тот же смысл, разные поля).
10. **Семантика «GO» не одна:** Owner `GO` для `/opsx-projectize:GO` (`.cursor/commands/opsx-projectize.md`), `UPDATE GO` только для сопровождения GRAPH (`.cursor/commands/opsx-pipeline.md`), `GO` для commit/devops/fix-bug, и отдельно verify/archive (`mode=archive` + записанный GO в override `.cursor/commands/opsx-verify.md` vs краткое «verify GO» в `openspec/config.yaml`).

**Первый фикс:** в одном месте (лучше всего — секция post-impl в `.cursor/commands/opsx-apply.md` под TARGET OVERRIDE, со ссылкой на `.cursor/pipeline/GRAPH.md`) зафиксировать единый обязательный spine после implementation: либо plan-verification → next-check → bounded executors → verify, либо явно объявить legacy-ветку verify mode=impl устаревшей для game-target, чтобы NAVIGATE и apply не расходились.
