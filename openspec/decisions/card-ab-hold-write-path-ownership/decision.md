# Decision: Card A/B Hold Write-Path Ownership

## Status

Accepted

## Context

Режим A/B Hold затрагивает write-path рекламы: setup ключей/whitelist, фиксацию и запрет обновления целевых позиций, guard перерасхода, freeze разрешённого набора фраз (allowed-set PG snapshot + enforcement исключения не-разрешённых фраз во время hold; минус — derived), а также координацию bot-пода и shop-runner-пода через Redis. Ordinary V3 preamble, minus-phrase auto-update и параллельные ACT-корутины уже пишут в те же сущности (ключ / БС / ЦП / ставки / минус-фразы). Без reusable правила ownership любой «if в orchestrator» или ручное переключение legacy-флагов снова смешает normal updater с hold и сделает A/B-тест карточки нестабильным.

Accepted decision `openspec/decisions/mode-defaults-policy-ownership/decision.md` закрывает только placement дефолтов paid/free overlays (в т.ч. `auto_update_minus_phrases`). Он не отвечает, кто владеет setup/hold write-path, какие ACT-пути должны быть заморожены (включая минус-фразы), когда UI может заявить готовность A/B, как PG-состояние режима / snapshot соотносится с Redis-прерыванием между подами, и **запрещён ли Excel как write-path режима** в MVP.

Production bug: Excel `import_apply` мог выставить `card_ab_hold_mode=active` (или `pending_setup`) без ENTER allowed-set snapshot; `process_ab_setup` не бежит для уже ACTIVE → freeze/enforcement пустой или stale; UI ready-after-ACTIVE может врать.

## Decision

A/B Hold — отдельный paid automation write-path с durable состоянием в кампании и cross-pod interrupt в Redis.

1. **Ownership pipeline:** setup ENTER и hold-тик принадлежат выделенному A/B Hold automation path в shop-runner (отдельные entrypoints / pipeline для setup и hold). Ordinary V3 NORMAL preamble не является владельцем структурных изменений на время PENDING_SETUP / ACTIVE.
2. **Scheduling:** при состоянии режима PENDING_SETUP или ACTIVE кампания MUST NOT планироваться в ordinary V3 structural update; запускаются только setup (пока PENDING_SETUP) или hold (пока ACTIVE).
2a. **Stats freshness asymmetry:** включение режима (**paid Telegram UI** → PENDING_SETUP) MUST быть запрещено, если кампания не проходит тот же класс проверки свежести/доступности статы, что `_split_advs_by_stats_freshness` / попадание в `advs_filtred` (проблемы получения статистики по РК). После успешного переключения (PENDING_SETUP или ACTIVE) setup/hold MUST планироваться из полного eligible списка кампаний и MUST NOT блокироваться отсутствием в `advs_filtred` — сбои свежести статы после входа не должны оставлять РК в вечном PENDING и не должны отменять hold-тик только из‑за freshness gate.
2b. **Enable UX on stats block:** при отказе enable из‑за проблем статы пользователь MUST сразу видеть причину, текст ограничения и рекомендацию обратиться в поддержку/к админу со ссылкой `app.client_bot.const.SUPPORT_LINK` (в кодовой базе нет singular `ADMIN`; whitelist админов — `ADMINS`; публичная ссылка поддержки для пользователя — `SUPPORT_LINK`).
2c. **Launch validity soft-gate (низкий объём показов):** при попытке enable (**paid Telegram UI** → PENDING_SETUP), после прохождения freshness/health гейта (§2a), система MUST оценить суммарные недавние показы keyword-clusters кампании как **campaign-level proxy** (не фильтр по setup non-BAD / would-carry-test ключам): реюз `full_wb_adv_stat.get_keywords_views_by_days` по `adv_id` (+ парный `search_adv_id`) из MV `default_db.mv_clusters_daily_agg` — тот же класс CH-источника, что карточки ключей. Зерно окна — **календарные дни MV**, покрывающие last-24h wall-clock (inclusive `date BETWEEN` по суткам агрегата), а не true rolling 24h hour-buckets. Если измеренная Σ ниже минимального порога, enable MUST NOT выполняться молча: пользователю MUST быть показана причина (мало показов для надёжного A/B-теста), рекомендация поднять план max CPO и повторить попытку, и явный выбор «всё равно запустить» / «отмена». До выбора mode MUST оставаться `OFF`; «всё равно запустить» → `PENDING_SETUP` + Redis ENTER; «отмена» → `OFF` без ENTER. Если CH unavailable / query error — **отдельный soft reason** (объём показов временно недоступен), mode остаётся `OFF`, ENTER не сигналится; MUST NOT трактовать ошибку как 0 показов и MUST NOT показывать low-impressions warning так, будто объём успешно измерен. Это **soft-gate** (предупреждение, не hard block; пользователь MAY продолжить на свой риск при measured low volume), в отличие от freshness hard-block (§2a) и правила пустого allowed-set (не-ready, §8). Порог и UX-copy — implementation-деталь design; owner — тот же bot enable write-path (paid Telegram UI), что §2a/2b. Keyword-filtered aggregate по setup-кандидатам и true rolling 24h — **out of MVP / future**.
3. **Structural freeze:** пока режим PENDING_SETUP или ACTIVE, структурные ACT-пути MUST NOT менять whitelist, целевые позиции, разгон/enable ключей, emergency structural mutations и ordinary recalculation минус-фраз (см. §8: snapshot + restore). Bidder path (ставки к уже зафиксированным ЦП) MUST оставаться разрешённым. Continuous ordinary Search **common bid** (общая ставка аукциона, `update_common_bid_in_search_adv`) MUST NOT — это не bidder; one-shot reset-to-min на ENTER — §19.
4. **Durable vs ephemeral:** PG-состояние режима (OFF / PENDING_SETUP / ACTIVE) — source of truth «в каком режиме живёт кампания». Redis signal / last-abort / setup-lock — только cross-pod координация прерывания и single-flight setup; Redis не заменяет PG-режим.
5. **Interrupt:** cooperative abort normal/hold тика через Redis signal читается в shop-runner; штатный early return до apply считается безопасным («остановлено, можно продолжать»). Abort mid-apply недопустим как штатный путь.
6. **Paid boundary:** enable / UI режима — только при `bot_active is True`. При `bot_active is False` UI скрыт, enable MUST NOT выполняться.
7. **Defaults:** дефолт режима «выкл» при paid/free overlays подчиняется `openspec/decisions/mode-defaults-policy-ownership/decision.md` (declarative overlays), не transition-helper и не UI-handler.
8. **Allowed-phrase-set freeze + PG snapshot + UI readiness:** **primary invariant** режима — заморозить **разрешённый (relevant) набор фраз** кампании (relevant-фразы + получившийся GOOD/whitelist профиль ключей), а не список минус-фраз. Минус-лист — **производный механизм принудительного исключения** (derived enforcement), а не замораживаемая сущность. Переиспользуется существующая модель `auto_add_only_relevant_phrase` / `relevant_phrases` / `NOT_RELEVANT_PHRASE` (не-разрешённая фраза → BAD → минус). allowed-set snapshot хранится durable в PG; UI «можно запускать A/B» только после полного setup.
   - **ENTER / PENDING_SETUP (жёсткий порядок до ACTIVE):** (1) зафиксировать разрешённый набор фраз (relevant-фразы + GOOD/whitelist тексты ключей) и сохранить как durable allowed-set snapshot в PG (новое durable поле — **новая Alembic migration**, т.к. upgrade поля режима уже был); (2) одной setup-мутацией / sync привести WB к этому состоянию — исключить (минус) всё, что вне allowed-set, в пределах WB minus cap (не ordinary recalculation loop); (3) завершить остальной setup профиля (критерии ключей / ЦП / БС); (4) только после успешной записи allowed-set snapshot и всего выше setup MAY считаться завершённым и mode → **ACTIVE**.
   - **UI readiness (исключая гонку):** интерфейс MUST NOT сообщать, что режим включён и можно запускать A/B-тесты, пока mode ≠ **ACTIVE** после успешного завершения setup (включая allowed-set snapshot). Ответ «можно тестировать» на одном PENDING_SETUP / «запрос принят» без полного setup — Forbidden. Redis interrupt / setup lock MUST исключать готовность UI при незавершённом или прерванном setup.
   - **PENDING_SETUP / ACTIVE (hold enforcement ≠ ordinary recalculation):** ordinary recalculation / auto-update минус-фраз — то есть пересчёт GOOD/BAD по свежей стате и **изменение** allowed-set — MUST NOT (allowed-set заморожен). Отдельно и независимо от этого, hold-protection MUST поддерживать фактическую поверхность трат равной замороженному allowed-set: любые новые / не-разрешённые фразы, появившиеся после ENTER, MUST исключаться (минус как enforcement), а разрешённые фразы, снятые вручную, MUST восстанавливаться. Ручные правки в боте или кабинете WB считаются нарушением freeze и перезаписываются. Bot callback ordinary minus refresh («Обновить минус-слова») при freeze MUST NOT сообщать success; MUST объяснить, что набор фраз зафиксирован и для изменений нужен EXIT / disable A/B Hold. Silent no-op с «Минус-слова обновлены» — Forbidden.
   - **WB minus cap (видимая деградация, не тихий обман):** enforcement производного минус-листа ограничен лимитом WB (~1000 фраз на nmid). Если для удержания замороженного allowed-set требуется исключить больше фраз, чем допускает cap, система MUST деградировать **видимо** (лог ERROR/WARN + честный статус, что hold **не может** гарантировать чистую поверхность для этой РК) и MUST NOT молча заявлять чистый hold. Для типов кампаний с открытым матчингом (open-match), где controllability через минус не доказана реализацией, freeze — **best-effort**, а не гарантированный; UI / справка не должны обещать полную заморозку без привязки к типу РК и cap-feasibility.
   - **EXIT → OFF:** ordinary auto-update минус-фраз и recalculation allowed-set снова разрешены; allowed-set snapshot clear/archive; UI снимает статус готовности теста.
   - Allowed-set snapshot — durable SoT в PG рядом с mode; Redis не заменяет PG-snapshot разрешённого набора фраз.
9. **Excel write-path (MVP — out):** Excel roundtrip MUST NOT экспортировать, импортировать или применять `card_ab_hold_mode` (колонки нет; если значение всё же попало в payload — apply MUST NO-OP / ignore). Excel MUST NOT переводить режим в `pending_setup`, `active` или `off`. Единственный enable/disable write-path в MVP — **paid Telegram UI** (ENABLE from `OFF` → PENDING_SETUP + Redis ENTER → setup → ACTIVE; DISABLE → OFF + clear allowed-set snapshot). Прямой переход в `ACTIVE` любым non-setup путём (в т.ч. бывший Excel setattr) — **Forbidden** (§8). Excel-колонка / Excel enable A/B Hold — **future / out of MVP** (идея сохранена, не текущий контракт).
10. **Telegram Enable idempotent while PENDING_SETUP / ACTIVE:** Enable MUST NO-OP (mode unchanged; no Redis ENTER rewrite; no re-trigger of ENTER `force_ab_hold_setup_sync`) when mode is already `PENDING_SETUP` or `ACTIVE`. Demote `ACTIVE`→`PENDING_SETUP` via Enable — **Forbidden** (ломает minus freeze / re-runs ENTER sync mid-hold). EXIT → `OFF` (+ clear snapshot) — единственный MVP path перед новым ENTER. In-flight shop-runner setup при стабильном `PENDING_SETUP` (lock) — Allowed и не считается re-ENTER от Enable. Handler no-op remains the safety net even if the button is still visible or a stale callback arrives.
11. **Telegram keyboard MAY hide Enable while PENDING_SETUP / ACTIVE:** A/B Hold screen keyboard MUST always offer Disable and Back. Enable MUST be offered when mode is `OFF` (subject to paid/access gates). When mode is `PENDING_SETUP` or `ACTIVE`, the UI MAY omit the Enable button to reduce accidental presses; this is Allowed UX and does not change write ownership. Hiding Enable MUST NOT be the sole protection — §10 handler no-op remains mandatory.
12. **A/B Hold — только V3 auto-updater + взаимоисключение с V2:** enable A/B Hold MUST быть разрешён только при `automatic_version == 3`; enable на не-V3 РК — no-op (mode остаётся `OFF`) + причина «A/B Hold требует V3». Пока mode `PENDING_SETUP` / `ACTIVE`, переключение версии авто-апдейтера на V2 MUST быть заблокировано (сначала EXIT → `OFF`). Owner: paid Telegram enable handler (`enable_card_ab_hold` / `ui_access`) — V3-gate рядом с paid/freshness gates; `auto_updater_version_toggle` handler — downgrade-block при активном режиме. Авто-переключатель стратегии РК (`change_adv_strategy`, MIN_CPO/MAX_CONV) — **V2-scope** и вне structural freeze §3: A/B Hold не добавляет отдельный freeze-гард на этот путь, а held V3-профиль MUST NOT управляться этим campaign-level strategy objective. Развязка V3 keyword `strategy_mode` от `AdvSetting.strategy` — отдельная задача вне этого change (не в scope decision).
13. **Shared defaults application ≠ A/B Hold disable path:** shared campaign-defaults application (`apply_defaults_to_adv_setting`, «Применить дефолты» single/shop-wide handlers) MUST NOT disable/mutate A/B Hold на кампании в `PENDING_SETUP` / `ACTIVE`: MUST NOT форсить `card_ab_hold_mode=off`, MUST NOT очищать / оставлять stale allowed-set snapshot, MUST NOT сбрасывать A/B-Hold-coupled структурные поля (`automatic_version`→non-V3, whitelist/target-place automation, bidder profile) в обход freeze / V3-only. Disable — только owned paid Telegram EXIT (§9). Для `OFF`-кампаний defaults применяются как обычно. §7 (default off via overlays для новых / сброса) не отменяется; §13 запрещает именно un-owned disable held-кампании.
14. **PENDING_SETUP liveness (нет молчаливого вечного semi-frozen состояния):** поскольку PENDING_SETUP исключает кампанию из ordinary automation (§2/§3), кампания MUST NOT оставаться в PENDING_SETUP неопределённо долго, когда setup заблокирован детерминированным / user-fixable условием, без видимой причины и пути восстановления. Owner — тот же A/B Hold enable/setup write-path (§2a/§2c/§8), не ordinary preamble и не shared defaults.
    - **14a. ENTER precondition — plan max CPO:** enable (**paid Telegram UI** → PENDING_SETUP) MUST быть hard-blocked, если план `max_price_for_order` отсутствует или ≤ 0 (значение, которое setup требует для классификации ключей). Mode остаётся `OFF`; пользователь видит причину (задать положительный план max CPO) и повторяет. Это hard-gate рядом с §2a freshness и §12 V3-only, проверяется до записи `PENDING_SETUP` + Redis ENTER и **до** §2c soft-gate (нет смысла предупреждать про объём, если max CPO = 0). Rationale: без положительного max CPO `process_ab_setup` детерминированно делает early return каждый тик и никогда не доходит до ACTIVE.
    - **14b. Actionable non-ready status:** пока PENDING_SETUP, если setup не может прогрессировать по детерминированной причине, детектируемой только на setup-тике (например пустой allowed-set / нет non-BAD keyword-поверхности, либо max CPO пропал после enable), UI-статус MUST называть конкретную причину и рекомендованное действие (поднять max CPO / нет подходящих ключей / отключить A/B Hold), а не только generic «Подготовка…». Транзиентные причины (lock contention, единичный stale-тик, warmup кэша ключей) MAY оставлять generic preparing-статус.
    - **14c. Bounded recovery (MVP — EXIT-owned):** детерминированный блок setup MUST NOT удерживать кампанию в молчаливом semi-frozen состоянии вечно. MVP-минимум: EXIT всегда доступен (§9) **и** actionable-причина (14b) присутствует, так что пользователь всегда может восстановиться (исправить max CPO и дождаться следующего тика, либо EXIT → OFF → ordinary automation). Owned авто-abort-to-OFF после ограниченного числа/длительности детерминированных неудач setup — **SHOULD / future** (потребует durable `pending_since` timestamp + setup-watchdog; вне текущего MVP-scope). Silent indefinite PENDING без причины и без доступного EXIT — Forbidden.

> **Update (owner product flow — WARM_UP / confirm / epoch):** §3 «ENTER criterion» и §4 «HOLD invariants» описывают исторически применённую MVP-1 модель, в которой target place фиксировался синхронно с автоматической PASS/FAIL классификацией на ENTER. Owner-approved продуктовое требование (не `REQ-AB-HOLD-BUDGET-SAFETY-001`) заменяет момент фиксации target place: целевая позиция теперь фиксируется **только** после отдельной durable стадии WARM_UP (default/min 24 часа) и явного подтверждения пользователем (keyword-set confirm → WARM_UP → TP confirm → Auto participation confirm → Auto bid confirm → durable PENDING intent → WB sync → ACTIVE), а не автоматически на ENTER-тике. §3/§4 остаются источником критерия eligibility ключа (`pay_for_order ≤ max CPO`, `views ≥ 100`) и общего инварианта «биддер продолжает работать к зафиксированным целям», но фраза «PASS → set target_place = current WB position» **больше не описывает текущий owner-approved контракт фиксации TP** — она замещена §15/§16 и `ab-hold-epoch-lifecycle-and-generation-ownership` / `ab-hold-confirmed-epoch-parameters-sot`. Silent auto-ENTER-классификация без явных подтверждений keyword+TP+Auto, фиксация TP без durable WARM_UP и HOLD без durable WARM_UP — Forbidden (см. §15/§16 Forbidden).

15. **WARM_UP / epoch / generation lifecycle (см. `ab-hold-epoch-lifecycle-and-generation-ownership`).** Durable pre-epoch стадия WARM_UP (default/min = 24 часа, пользователь MAY увеличить, MUST NOT уменьшить ниже 24ч), запускаемая явным подтверждением набора ключей; ручное изменение набора ключей во время WARM_UP завершает текущий таймер и запускает новый; во время WARM_UP MUST NOT авто-добавление ключей и MUST NOT авто-возврат исключённых, safety-исключение Allowed, target place не фиксируется. Порядок до ACTIVE: durable PENDING intent (все confirmed-параметры + generation) записывается в PG **до** первой WB-мутации этой generation; partial/failed WB sync оставляет кампанию non-ACTIVE с сохранённым generation; retry переиспользует тот же generation и confirmed-параметры без пересчёта TP/Auto bid и без создания новой эпохи. Owner — A/B Hold epoch/setup write-path, не ordinary preamble и не Telegram-хендлер напрямую.
16. **Confirmed epoch parameters SoT (см. `ab-hold-confirmed-epoch-parameters-sot`).** Подтверждённый набор ключей, подтверждённые target places, подтверждённое участие Auto и подтверждённая ставка Auto — durable epoch-параметры, отдельные от факт-состояния WB. Факт-позиция ключа (текущая наблюдаемая) и target place (предложенный через `ab_hold_target_place_from_keyword(position)`, затем подтверждённый) — раздельные семантические поля на экране и в хранилище; их числовые значения MAY совпасть после округления/clamping, но это MUST NOT становиться причиной слияния полей. После подтверждения target place durable и immutable внутри эпохи; ENTER/setup MUST NOT его пересчитывать; обычный дрейф факт-позиции MUST NOT переоткрывать подтверждение. Keyword bidder в ACTIVE — только holder подтверждённых target places (не добавляет/не возвращает ключи, не меняет target place). Auto participation confirm и Auto bid confirm — отдельные явные подтверждения, не подразумеваемые друг из друга и не подразумеваемые из Search keyword confirm; после ACTIVE ordinary Auto bid auto-update MUST NOT менять подтверждённую ставку Auto — **включая** `AutoResetBidService.ensure_auto_bids_minimum` (shop-runner) и peer Auto CPM writers.
16a. **Legacy setup race (pre-apply REQUIRED, `tasks.md` §18.4).** Пока epoch phase / durable PENDING intent не существуют, `process_ab_setup` MUST NOT auto-ACTIVE и `setup_apply` MUST NOT писать TP на ENTER PASS. Planned PG columns: `tasks.md` §19.5 / §22.5.
17. **Stale/missing stats freeze распространяется на Search/Auto bid-мутаторы (не только §2a enable-gate).** Отдельно от §2a (enable-gate на freshness) и §2c (soft-gate объёма), пока кампания в WARM_UP, PENDING или ACTIVE, при stale/missing статистике по ключу или кампании: (a) включение и исключение ключей (keyword inclusion/exclusion, в т.ч. hold-enforcement §8, safety-исключение WARM_UP, **и ENTER/setup Classification FAIL→OFF** через `apply_ab_hold_setup_mutations` / epoch-managed `process_ab_setup`) MUST замереть для затронутого ключа/кампании — не выполнять решение на «неизвестных» данных; (b) мутации ставки Search и мутации ставки/участия Auto (`change_adv_strategy`-класс путей, ordinary bid auto-update) MUST замереть по той же причине. Freeze охватывает решения (включение/исключение, изменение ставки), а не existence кампании: stale/missing статистика **MUST NOT** быть самостоятельной причиной остановки кампании — это отдельный, более сильный шаг, не покрываемый одним лишь stats-freeze. Freeze reconciles с §2a/§14a/§14b (enable/PENDING-gates остаются отдельными, более ранними проверками) и с §15/§16: WARM_UP-таймер продолжает идти при stale stats (freeze не останавливает время, только мутации), а уже подтверждённые (durable) target place/Auto bid не пересчитываются независимо от freshness — freeze здесь защищает **несостоявшиеся** решения (какие ключи войдут/выйдут, как измениться ставка), а не подтверждённые epoch-параметры (которые в любом случае immutable по §16).
   - **Carve-out (PBH-005 / soft MVP):** §17 freeze covers **unsettled decide-class** mutations only (keyword inclusion/exclusion **including setup FAIL→OFF**; ordinary Search/Auto bid auto-update). After a durable PENDING activation intent exists for the epoch, **apply snapshot** — writing that intent’s confirmed parameters to PG and synchronizing them to WB (`apply_confirmed_intent_to_pg` / `sync_intent_to_wb` class paths) — **MUST NOT** be blocked solely because campaign/keyword stats are stale or missing. Stale MAY still freeze decide-class paths on the same tick. MVP default safety stance = **soft** (freeze decide; do not abort/reset the epoch solely on stale; EXIT remains explicit). Setup FAIL→OFF on stale is **not** soft MVP and is **Forbidden** (PBH-001). Pre-start hard|soft|self picker and anti-drain are out of this decision’s owed scope (see `DOTO/WORKLOG.md` parks `[deferred-from:card-ab-hold-mode]`).
18. **Daily budget / activity-control — ортогональный reuse существующего контроллера, не отдельная финансовая safety-модель.** A/B Hold переиспользует существующий daily budget / campaign activity-control controller (например `ensure_campaigns_active` / auto-budget watchdog, см. §3 Allowed «orthogonal reversible activity-control») как есть: стоп-порог (stop threshold), а не жёсткий cap; перерасход (overshoot) относительно порога возможен и не гарантированно ограничен числом ввиду задержки статы, каданса воркера, in-flight трат, конкурентных write-путей и top-up, не обрезаемого до остатка бюджета; суточный сброс (daily reset) и возобновление трат на следующий день после сброса — ожидаемое поведение, не дефект. Этот decision и его дочерние (`ab-hold-epoch-lifecycle-and-generation-ownership`, `ab-hold-confirmed-epoch-parameters-sot`) MUST NOT вводить абсолютный бюджет теста, epoch spend cap, velocity cap, generic «financial latch», новую emergency-stop подсистему или global refill/restart suppression как часть A/B Hold write-path. Любая evidence-driven emergency-stop / monitoring-alerting инициатива — отдельный out-of-scope follow-on (не артефакт этого `opsx-continue`).
19. **Search common bid (общая ставка аукциона) — reset-to-min on ENTER, then freeze.** Search common bid (`SetCommonBids` / `update_search_adv_common_cpm`, ordinary path `CoroutinesManager.update_common_bid_in_search_adv`) — **рабочая** механика кампании, не мёртвый legacy: влияет на ещё не появившиеся / «холодные» ключи (в т.ч. до порога показов) и на ставку в каталоге. Это **отдельный** writer от cluster bidder (`update_cluster_bids`), который держит ставки к confirmed ЦП. Контракт под Hold:
   - **ENTER** (`OFF` → `PENDING_SETUP` + Redis ENTER / старт setup): A/B Hold **owned** path MUST **один раз** сбросить Search common bid по всем nm кампании на **WB minimum** (`search_adv_min_bids` / эквивалент SoT минимума). Continuous ordinary up/reset цикл MUST NOT выполнять этот сброс «заодно» как тиковый updater.
   - Пока mode `PENDING_SETUP` или `ACTIVE`: continuous ordinary `update_common_bid_in_search_adv` MUST NOT (Forbidden; structural freeze ordinary common-bid). Значение после owned reset остаётся на minimum до EXIT → `OFF` (или до нового ENTER после EXIT).
   - Повторный Enable mid-hold / demote — Forbidden (§10); повторный owned reset common-bid — только после EXIT → новый ENTER.
   - Owner one-shot reset: A/B Hold setup/ENTER write-path (тот же класс owner, что §8 setup), **не** ordinary common-bid updater и **не** bidder.
   - Bidder / `update_cluster_bids` в `ACTIVE` — без изменений (§3/§16): продолжает работать к зафиксированным ЦП.

## Forbidden

- Реализовывать hold только комбинацией legacy-флагов без durable режима и without exclusion из ordinary V3.
- Держать hold/setup structural логику внутри ordinary V3 NORMAL preamble как «ещё одну ветку if» без отдельного owner path.
- Останавливать биддер как способ «заморозить» позиции (в т.ч. через `bot_active=False` ради A/B).
- Менять whitelist / target place / enable / structural emergency ACT во время PENDING_SETUP / ACTIVE (кроме A/B setup/hold allowed paths и §8 allowed-set enforcement).
- Ordinary recalculation / auto-update минус-фраз (изменение allowed-set по свежей стате) во время PENDING_SETUP / ACTIVE (вместо freeze allowed-set + hold enforcement).
- Считать setup завершённым / переводить в ACTIVE без зафиксированного и записанного PG allowed-set snapshot.
- Молча заявлять чистый hold, когда enforcement замороженного allowed-set превышает WB minus cap или РК open-match без доказанной controllability (нужна видимая деградация).
- Сообщать в UI, что режим включён и можно запускать A/B, пока mode ещё PENDING_SETUP или setup не завершён (гонка с незавершённым / прерванном setup).
- Считать Redis единственным source of truth режима кампании или allowed-set snapshot без PG.
- Прерывать после успешного apply как штатный «safe abort».
- Отдавать UI или enable режима при `bot_active is False`.
- Задавать дефолт режима прямым присваиванием в transition-helper / handler в обход mode policy overlays.
- Включать A/B Hold (PENDING), когда кампания не проходит freshness/stats-health gate.
- Планировать setup/hold **только** из `advs_filtred`, оставляя PENDING без тика при stale stats.
- Silent enable-fail без причины и без рекомендации со `SUPPORT_LINK`.
- Молча включать A/B Hold (PENDING), когда измеренная Σ campaign-level keyword views (календарные дни MV / last-24h wall-clock cover) ниже порога, без причины, рекомендации поднять max CPO и явного выбора запустить/отмена (§2c).
- Трактовать CH unavailable / query error soft-gate §2c как «0 показов» или показывать low-impressions warning вместо отдельного soft reason (§2c).
- Требовать в MVP keyword-filtered Σ только по setup non-BAD / would-carry-test ключам или true rolling 24h поверх daily MV (§2c out of MVP).
- Excel export/import/apply колонки `card_ab_hold_mode` в MVP (включая enable `pending_setup`/`active` и disable `off` через Excel).
- Telegram Enable demote `ACTIVE`→`PENDING_SETUP` (или rewrite ENTER / restart force setup sync) while already `PENDING_SETUP` / `ACTIVE`.
- Прямой setattr / import `card_ab_hold_mode=active` (или `pending_setup`) минуя Telegram ENTER + `process_ab_setup` (§8).
- Включать A/B Hold на не-V3 РК (`automatic_version != 3`) или переключать РК на V2, пока mode `PENDING_SETUP` / `ACTIVE`.
- Добавлять A/B Hold freeze-гард на V2 `change_adv_strategy` или позволять campaign strategy objective менять held V3-профиль.
- Отключать / сбрасывать A/B Hold held-кампании (`PENDING_SETUP` / `ACTIVE`) через shared defaults / «Применить дефолты» в обход owned Telegram EXIT (§13).
- Enable → `PENDING_SETUP` при отсутствующем / ≤ 0 плане `max_price_for_order` (детерминированный вечный PENDING) без hard-gate (§14a).
- Молчаливый вечный `PENDING_SETUP` при детерминированном блоке setup — без actionable-причины (generic «Подготовка…») и без доступного EXIT (§14b/§14c).
- Тихая авто-классификация ENTER, фиксирующая target place без durable WARM_UP и без явных подтверждений keyword + TP + Auto (§15/§16 — заменяет прежнее §3 «PASS → set target_place = current WB position» как текущий контракт).
- HOLD/ACTIVE без предшествующего durable WARM_UP.
- Уменьшение WARM_UP ниже 24 часов; авто-добавление или авто-возврат ключей во время WARM_UP.
- Слияние факт-позиции и target place в одно поле/значение; пересчёт confirmed target place на ENTER, retry или из-за обычного дрейфа позиции.
- Продвижение generation или пересчёт TP/Auto bid на retry WB-синхронизации; переход в ACTIVE при partial sync.
- Абсолютный тестовый бюджет, epoch spend cap, velocity cap, generic financial latch, новая emergency-stop подсистема или global refill/restart suppression как часть A/B Hold write-path (§18).
- Трактовка daily budget controller как hard/epoch cap с гарантированным overshoot-пределом (§18).
- Перевод keyword inclusion/exclusion (включая ENTER/setup FAIL→OFF) или Search/Auto bid-мутации в решение при stale/missing статистике вместо freeze (§17 / PBH-001); либо остановка кампании исключительно по причине stale/missing статистики.
- Блокировать apply snapshot / WB sync уже записанного durable PENDING intent **только** из‑за stale/missing stats (§17 carve-out / PBH-005 Forbidden).
- Оставлять Search common bid завышенным и лишь «замораживать as-is» при ENTER без owned reset-to-min (§19).
- Continuous ordinary `update_common_bid_in_search_adv` up/reset цикл во время `PENDING_SETUP` / `ACTIVE` (§19).
- Выполнять owned common-bid reset через ordinary common-bid updater или через bidder/cluster path (§19).
- Повторный owned common-bid reset mid-hold без EXIT → новый ENTER (§10/§19).
- Framing, будто `REQ-AB-HOLD-BUDGET-SAFETY-001` или параллельная финансовая safety-модель — текущий scope этого change.

## Examples

Good:

- Клиент включает A/B Hold из Telegram при fresh stats → PG `PENDING_SETUP` + Redis signal ENTER → ordinary V3 тик abort до apply → setup: фиксация allowed-set (relevant + GOOD ключи) → PG allowed-set snapshot → sync WB к allowed-set → фиксация ЦП/БС → PG `ACTIVE` → UI: «режим включён, можно запускать A/B» → дальше hold + bidder + enforcement (исключение не-разрешённых фраз) при drift.
- Во время ACTIVE появляется новая фраза или пользователь меняет минус в кабинете WB → следующий hold-тик приводит поверхность к замороженному allowed-set (исключает не-разрешённые, восстанавливает снятые разрешённые); ordinary recalculation allowed-set не запускается.
- EXIT из Telegram → OFF → ordinary minus auto-update + recalculation allowed-set снова eligible; PG allowed-set snapshot cleared/archived; UI больше не показывает «можно тестировать» по hold.
- Клиент жмёт «Включить» при stale/stats problem → enable no-op; alert с reason + «обратитесь в поддержку» + `SUPPORT_LINK`; PG остаётся OFF.
- Клиент жмёт «Включить» при measured low campaign-level Σ (calendar-day MV cover) → soft-warn + launch-anyway/cancel; mode `OFF` до выбора (§2c).
- Клиент жмёт «Включить» при CH volume query error → distinct soft reason (объём недоступен), mode `OFF`, без low-impressions copy и без ENTER (§2c).
- Parallel `update_top_key_in_advs` / individual target-place updater видит ACTIVE и не выполняет structural write.
- PENDING_SETUP при последующем stale всё равно получает `process_ab_setup` (не застревает из‑за `advs_filtred`).
- Excel import с полем `card_ab_hold_mode` игнорируется / колонка отсутствует в schema; режим не меняется.

Bad:

- Только `if card_ab_hold_mode` внутри ordinary preamble без exclusion scheduling и без gates на соседних ACT-корутинах.
- Выключить `bot_active`, чтобы «не мешать тесту» (биддер тоже останавливается).
- Хранить режим только в Redis без PG.
- Enable при проблемах статы «втихую» или setup только для fresh → вечный PENDING.
- UI пишет «можно запускать A/B» сразу после PENDING_SETUP, до allowed-set snapshot и ACTIVE.
- Во время ACTIVE продолжает ordinary `update_minus_phrases` recalculation (меняет allowed-set) или игнорирует появление новых не-разрешённых фраз (они откручиваются).
- Excel import `card_ab_hold_mode=active` (или `pending_setup`) через `can_apply_card_ab_hold_mode_via_excel` + setattr — ACTIVE без ENTER allowed-set snapshot.
- Telegram Enable на ACTIVE (или повторный Enable на PENDING) demote/rewrite ENTER и заново гоняет force setup sync mid-hold.
- Enforcement замороженного allowed-set требует больше фраз, чем WB minus cap, но бот молча рапортует чистый hold вместо видимой деградации.
- «Применить дефолты» (single или shop-wide) на `ACTIVE` РК молча ставит `off`, оставляет непустой allowed-set snapshot и сбивает `automatic_version` на V2 (un-owned disable в обход EXIT).
- Enable-хендлер фиксирует target place сразу после прохождения PFO/views-классификации, минуя WARM_UP и отдельные TP/Auto подтверждения.
- Экран показывает одно число «Позиция: 12» без разделения на факт и предложение/подтверждённый target place.
