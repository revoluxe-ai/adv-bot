# Owner Contract

## Что хотим получить

Укрепить границы существующего A/B Hold flow: перед подтверждением или
отключением callback должен проверять принадлежность текущего Telegram-
пользователя кампании через существующую связь с кабинетом.

Ключ без положительной фактической позиции не должен участвовать в A/B Hold и
не должен приводить к сохранению target place `0`. Пользователь должен видеть
исключённые ключи и причины, а подтверждать только оставшийся валидный набор.

## Зачем

Отсутствующая или неположительная фактическая позиция не является валидным
основанием для участия ключа в эксперименте. Такой ключ нужно исключить из
набора участников, чтобы `target place 0` не попал в сохранённое состояние.

Отсутствие actor-check в callback path является authorization gap. Этот change
не утверждает наличие доказанного live-инцидента или эксплуатации.

## Что должно остаться неизменным

- Проверка выполняется через существующую связь Telegram-пользователь →
  кабинет кампании.
- Положительные позиции в разрешённом flow по-прежнему подтверждаются.
- Требование явного подтверждения параметров перед сохранением.
- Существующий lifecycle A/B Hold, WARM_UP и generation.
- Существующий durable state и PG/Redis lifecycle.
- Новая ownership model, durable ACL и user ID в callback не добавляются.

## Чего сейчас не делаем

- Не создаём новую ownership model, durable ACL или новую схему callback с user
  ID.
- Не меняем WARM_UP, generation или PG/Redis lifecycle.
- Не добавляем миграции и новые архитектурные решения.
- Не меняем billing и Pricer preview context.
- Не меняем PG/ClickHouse external-call coverage и migration tooling.
- Не проводим performance optimization.
- Не выполняем merge, push, PR или deployment.

## Как поймём, что получилось

- Перед подтверждением или отключением разрешённого callback проверяется
  принадлежность текущего Telegram-пользователя кабинету кампании.
- Чужой callback не выполняет confirm/disable, PG-write, Redis-cleanup или
  lifecycle transition.
- Ключи без фактической позиции или с неположительной фактической позицией
  отображаются как исключённые с причиной и не входят в подтверждаемый набор.
- `target place 0` никогда не сохраняется.
- Если после исключения не осталось валидных ключей, подтверждение не
  продолжается.
- Подтверждается только оставшийся валидный набор.
- Положительные позиции разрешённого flow по-прежнему сохраняются.

## Решения Owner

- **D-001:** Перед любым подтверждающим или отключающим callback-действием
  существующий handler обязан проверить, что текущий Telegram-пользователь
  связан с кабинетом кампании через существующий relation helper. Чужой
  callback не выполняет confirm/disable, PG-write, Redis-cleanup или lifecycle
  transition. Новая ownership model, durable ACL или user ID в callback не
  добавляются.
- **D-002:** Ключ без фактической позиции или с неположительной фактической
  позицией исключается из набора участников A/B Hold. Отсутствующая позиция не
  преобразуется в факт `0` и не становится `target place 0`. В подтверждение
  передаётся только оставшийся набор ключей с положительными фактическими
  позициями.
- **D-003:** Пользователь должен видеть, какие ключи исключены и почему. Если
  после исключения валидных ключей не осталось, подтверждение не продолжается.
  Положительные позиции разрешённого flow по-прежнему сохраняются.
- **D-004:** Существующий WARM_UP, generation, durable state, PG/Redis
  lifecycle, явные подтверждения и общий A/B Hold lifecycle остаются
  неизменными. Вне scope остаются новая ACL/ownership model, миграции, billing,
  Pricer preview, external-call coverage, performance optimization, merge,
  push, PR и deployment. Отсутствие actor-check считается authorization gap,
  но live exploitation не утверждается.
