## Context

В текущем Alembic-графе существуют две конечные ревизии:
`d1e2f3a4b5c6` и `f2a3b4c5d6e7`. Из-за этого будущая миграция не имеет
однозначной точки продолжения. Изменение ограничено восстановлением единственной
head без изменения уже опубликованной истории, схемы, данных или прикладной
логики.

Реализация должна добавить одну новую forward-only merge-ревизию с двумя
существующими родителями и обновить единственное ожидаемое значение в контрактной
проверке `test_exactly_one_alembic_head`. Проверяется только этот nodeid.

## Goals / Non-Goals

**Goals:**

- Свести две текущие Alembic head к одной итоговой head.
- Сохранить обе существующие ревизии неизменными.
- Зафиксировать итоговую head контрактной проверкой.

**Non-Goals:**

- Добавление DDL, миграций данных или прикладной логики.
- Изменение, удаление либо переписывание существующих миграций.
- Изменение других тестов, запуск миграций, деплой, commit, push, PR или
  архивирование change.

## Ownership & Placement

Владение изменением находится в слое Alembic migration topology: новая revision
file определяет только `down_revision` из двух текущих head. Контрактная проверка
владеет единственным ожидаемым идентификатором итоговой head.

Разрешённые слои: новая Alembic merge-ревизия и существующая выделенная проверка
head. Запрещённые слои: существующие revision files, ORM-модели, прикладные
сервисы, DDL и data-migration paths. Такое размещение соответствует proposed
decision: топология сходится добавлением forward-only узла, а не изменением
истории или побочными изменениями схемы.

## Decisions

### Одна пустая forward-only merge-ревизия

Новая ревизия должна иметь оба существующих идентификатора
`d1e2f3a4b5c6` и `f2a3b4c5d6e7` в `down_revision`, чтобы образовать один
следующий узел графа. `upgrade()` и `downgrade()` остаются без schema- и
data-операций.

Альтернатива — изменить parent-ссылку одной из существующих ревизий — отклонена:
она переписывает опубликованную историю и нарушает proposed decision.

### Контрактная проверка единственной head

В `test_exactly_one_alembic_head` должно измениться ровно одно ожидаемое значение:
на идентификатор новой merge-ревизии. Проверка выполняется одним nodeid, чтобы
доказать итоговую топологию без расширения тестового scope.

Альтернатива — ручная проверка через CLI без обновления теста — отклонена: она не
сохраняет воспроизводимый контракт для последующих изменений.

### Идентификатор новой ревизии

Идентификатор генерируется при создании единственной новой revision file и сразу
используется как её имя, итоговая head и ожидаемое значение в контрактном тесте.
Это исключает расхождение между топологией и ожиданием проверки.

## Risks / Trade-offs

- [Неверно задан один из родителей] → до обновления теста сверить, что
  `down_revision` содержит ровно `d1e2f3a4b5c6` и `f2a3b4c5d6e7`.
- [Тест ожидает не идентификатор новой ревизии] → обновить только одно
  существующее ожидание и выполнить `test_exactly_one_alembic_head` по nodeid.
- [В merge-ревизию попадут побочные операции] → оставить `upgrade()` и
  `downgrade()` пустыми; не добавлять DDL или data migration.

## Migration Plan

1. Создать единственную новую merge-ревизию после двух указанных head.
2. Не добавлять операций схемы или данных.
3. Заменить одно ожидаемое значение в `test_exactly_one_alembic_head` на
   идентификатор новой merge-ревизии.
4. Выполнить только этот nodeid.

Изменение не требует деплоя или запуска миграций в окружениях. До применения
новой ревизии откат состоит в удалении только новой revision file и возврате
единственного ожидаемого значения; существующие ревизии не меняются.

## Open Questions

Нет. Идентификатор merge-ревизии определяется только в момент её создания и
должен быть согласован с единственным ожиданием контрактного теста.
