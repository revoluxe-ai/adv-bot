# Owner Contract

## Что хотим получить

Единая стратегия получения, исторической загрузки, инкрементального накопления и контроля полноты максимально доступных данных магазина Wildberries.

Желаемый результат этой архитектурной работы: source strategy для товарных и рекламных dataset; правила выбора источника и сохранения исходной гранулярности; стратегия initial backfill и incremental collection; общий подход к rate limiting, scheduling и freshness; семантика coverage, error и provenance; границы последующих независимых implementation changes.

## Зачем

Сбор, история и полнота данных магазина должны быть одной стратегией, чтобы ZIP не запускал полный обход WB API, а сбор не смешивался с управлением кампаниями.

## Что должно остаться неизменным

Сбор не включает управление рекламными кампаниями. Статистика Авто и Поиска не сливается. Итоги кампании не раскладываются на артикулы без breakdown источника. ZIP читает уже накопленное в PostgreSQL и ClickHouse.

## Чего сейчас не делаем

Не реализуем collectors, CSV poller, базу данных и ZIP exporter. Не управляем и не создаём кампании. Не делаем AI return JSON, preview/apply и Telegram UI. Не дублируем shop-wide-campaign-data-collection и не дублируем формат AI Package из ai-package-v1-contract.

## Как поймём, что получилось

Есть зафиксированная стратегия источников и накопления. Для dataset ясны источник, зерно, история, обновление, права, подписка и причина неполноты. Оперативный сбор, backfill и CSV разделены. Неполнота различается машинно-читаемо. Границы следующих implementation changes названы и не пересекаются с shop-wide-campaign-data-collection и с форматом пакета ai-package-v1-contract. Источник товарных заказов и продаж не выбран окончательно без evidence. Непроверенные лимиты API не помечены как подтверждённые.

## Решения Owner

1. Подключённый магазин собирает данные по всем своим артикулам и всем доступным рекламным кампаниям независимо от того, подключены ли РК к управлению WB Sky.
2. Сбор данных и управление РК — разные контуры. Сбор не меняет bot_active и не предоставляет новых write permissions.
3. Базовая аналитическая единица — nm_id. Связь nm_id ↔ campaign_id — многие-ко-многим. Авто (полки) и Поиск (ключи) имеют собственные идентификаторы и статистику; связь пары сохраняется отдельно.
4. Не распределять статистику уровня кампании между артикулами без подтверждённого источником breakdown.
5. Основной источник AI Package — накопленные данные PostgreSQL/ClickHouse. Формирование ZIP не должно запускать полный сбор магазина через WB API.
6. Для каждого dataset определить допустимые источники, гранулярность, доступную историю, правила обновления, права, зависимости от подписки и причины неполноты.
7. Оперативный сбор, исторический backfill и асинхронные CSV-отчёты рассматриваются как разные режимы. Не обходить ограничения API увеличением периода запроса.
8. Отсутствие данных, недостаточные права, отсутствие подписки, частичный сбор и ошибка источника должны различаться машинно-читаемым образом.
9. Новые фоновые задачи не должны нарушать лимиты WB API и вытеснять работающие production collectors.
