# Design — ai-package-multi-window-analysis

## Context

PR #450 (`19ec4bf5ac0a6e16a1c43699a01232dc2d55cbd9`, draft, не этот change) делает Full AI Package самоописываемым: `PACKAGE_SUMMARY`, единый статус семейств, физический `adv_id`, честные GAP. Этот change его не редактирует.

На `origin/stage` уже есть:

- `ExportPeriod` — включительный календарный период вызывающей стороны. Ключевая история им не обрезается. Дневная campaign stat в текущем чтении обрезается этим периодом и проецирует только показы и клики.
- `PackageCutoff.last_closed_calendar_day` — UTC-дата `generated_at` минус один календарный день. Это номинальная граница окон пакета (`package_cutoff_date`). Она не доказывает, что отчёт WB за этот день закрыт. Часовой пояс отчётности WB остаётся `UNKNOWN`.
- Каталог окон ключевой истории: `1d`, `3d`, `7d`, `14d`, `30d`, `90d`, `180d`, `365d`, предыдущие такие же отрезки, MTD/QTD/YTD, предыдущий месяц/квартал/год, позапрошлый год, `all_available`. Конец стандартного окна — `last_closed_calendar_day`. Это полные UTC-дни, не скользящие 24 часа.
- Таблица `default_db.full_adv_wb_stat` хранит на зерне физический `adv_id` + дата: показы, клики, расход, корзину, заказы, сумму заказов. Часовая производная не является нормой дневного окна.
- `keyword_windows` уже агрегирует ключевое зерно. Это самый тяжёлый аналитический файл. Повторно материализовать его под другим именем нельзя.
- Семейство `store_drr` и товарные заказы/продажи магазина в пакете — GAP. Числитель Store DRR в сборе общих продаж остаётся `BLOCKED_BY_CAMPAIGN_COVERAGE`.
- Заказы и сумма в campaign stat не классифицированы как прямая или связанная атрибуция. Воронка `wb_common_stat` ограничена основным артикулом комплекса и не является выручкой магазина.

Ограничение: экспорт read-only, без WB API, без коллекторов, без DDL. ZIP — транспорт доменного контракта.

## Goals / Non-Goals

### Goals

- Один доменный расчёт окон для магазина, физической ноги и допустимого товарного зерна.
- Контракт метрик, который можно расширять идентификаторами без смены смысла старых.
- Инструкция AI, которая запрещает подменять пропуски нулями и выдумывать причинность.
- Сравнения с явной сопоставимостью.
- Та же семантика для будущего API и MCP.

### Non-Goals

См. proposal. Дополнительно: не заводить новую таблицу агрегатов, не заменять сырые факты недельной/месячной копией, не объявлять часовую таблицу источником «1 дня», не реализовывать режим управления ставкой.

## Architecture

```text
Canonical facts/history
        ↓
AnalysisAggregationService
        ↓
AnalysisContract
        ↓
ZIP / API / MCP transports
        ↓
AI_ANALYSIS_GUIDE interpretation
```

Сервис читает канонические дневные факты на диапазоне окон. Он не переписывает сырые файлы. Транспорт кладёт результат рядом с фактами.

### Файлы пакета

| Путь | Роль |
|---|---|
| `analysis/ANALYSIS_CONTRACT.json` | Нормативная машинная семантика, версия контракта |
| `analysis/AI_ANALYSIS_GUIDE.md` | Порядок чтения и запреты для AI |
| `analysis/windows/package_campaign_scope.jsonl` | Сумма физических ног, реально вошедших в охват пакета, на окно. Область `PACKAGE_CAMPAIGN_SCOPE` |
| `analysis/windows/campaigns.jsonl` | Физическая нога × окно |
| `analysis/windows/keyword_product_scope.jsonl` | Артикул × нога × окно только из ключевой истории. Область `KEYWORD_PERFORMANCE_PRODUCT_SCOPE` |
| `analysis/comparisons.jsonl` | Пары окон и статус сопоставимости |
| `keyword_performance/keyword_windows.jsonl` | Уже существующая ключевая витрина; не дублируется |

`analysis/windows/keywords.jsonl` не создаётся. Указатель в контракте ведёт на существующий ключевой файл. `analysis/windows/shop.jsonl` и `analysis/windows/products.jsonl` не создаются: эти имена читаются как весь магазин и вся экономика артикула. Файл артикула — свёртка уже имеющегося ключевого зерна (артикул × нога × окно), не копия запросов и не размазывание кампанийной статистики по артикулам. В каждой строке обязательна область `KEYWORD_PERFORMANCE_PRODUCT_SCOPE`. Из неё нельзя вывести все продажи артикула, всю его выручку, DRR артикула, заказы товара магазина или прямую/связанную атрибуцию.

### Поля строки окна

Идентичность сущности, `window_id`, `window_start`, `window_end`, покрытие, доступный диапазон источника, метрики, размеры выборки, `reason_codes`. Метрика, которую нельзя посчитать, отсутствует как значение и присутствует как причина. Ноль пишется только если источник наблюдал ноль.

Порядок строк детерминированный: сущность, затем `window_id` в порядке каталога.

### Анализ против истории

Контракт и summary-расширение называют, не подменяя уже существующие поля карты данных:

| Поле | Смысл |
|---|---|
| `requested_period` | Период вызывающей стороны (`ExportPeriod`). Не клиппинг ключевой истории |
| `analysis_windows` | Каталог и явный произвольный период, по которым посчитаны витрины |
| `history_context` | Доступная история семейства шире или уже любого одного окна |
| `package_cutoff_date` | Номинальная граница пакета: UTC-дата `generated_at` минус один день. Не полнота источника |
| `nominal_window_end` | Конец конкретного окна. У стандартных окон равен `package_cutoff_date` |
| `source_available_range` | Первый и последний день, который источник вообще отдал |
| `source_complete_through` | Последний день, который этот источник доказал как полный. Пусто, если доказательства нет |
| `effective_covered_range` | Пересечение номинального окна с наблюдаемыми днями |
| `coverage_status` | `COMPLETE`, `PARTIAL`, `NO_DATA` или `GAP` по доказательству источника, не по границе пакета |

Поля `latest_complete_date` нет. Инструкция AI обязана сказать дословно: package_cutoff_date is not evidence of source completeness.

AI не имеет права считать, что все строки пакета лежат внутри запрошенного периода.

## Decisions

### 1. Переиспользовать каталог окон

Стандартные окна сервиса — тот же список, что у ключевой истории, включая `14d`. Удалять `14d` нельзя: это уже норма. Номинальный конец — `package_cutoff_date`, интервал `1d` равен `[package_cutoff_date, package_cutoff_date]`. Это не 24 часа от `generated_at` и не доказательство закрытого отчётного дня. Часовая таблица не задаёт это окно. Часовой пояс отчётности WB не выдумывается и остаётся `UNKNOWN`, пока авторитетная семантика источника его не докажет.

Окно `1d` MUST NOT получать `coverage_status=COMPLETE` только потому, что его конец совпал с `package_cutoff_date`. Пример: граница пакета `2026-10-05`, а кампанийный источник доказал полноту только по `2026-09-25`. Тогда кампанийное окно `1d` на `2026-10-05` — `NO_DATA`, `PARTIAL` или `GAP` по доказательству источника, не «последний полный день». `source_complete_through` пуст, если источник не доказал ни одного полного дня.

Календарный год не равен `365d`. Текущий год — year-to-date до `package_cutoff_date`, не до 31 декабря. Предыдущий и позапрошлый год остаются отдельными идентификаторами. Для каждого более старого UTC-года, который пересекается с доступной историей кампанийного зерна пакета, добавляется `calendar_year_YYYY` только на зерне ноги и охвата пакета. На ключевое зерно эти дополнительные годы не размножаются.

Произвольный период получает `window_id = requested_custom` и не входит в список пресетов. Если он захватывает дату сборки пакета или будущее, окно не называется `1d`, а покрытие считается по источнику, не по границе.

### 2. Откуда брать числа

Кампанийная витрина читает дневной `full_adv_wb_stat` на диапазоне окон, последняя версия на пару нога+день, а не урезанный CSV текущего периода (в нём нет расхода и заказов). Ключевая витрина остаётся существующим расчётом. Строка охвата пакета — сумма различных физических ног, которые реально вошли в этот пакет и этот источник, с областью `PACKAGE_CAMPAIGN_SCOPE`. Она MAY быть посчитана сейчас, потому что состав слагаемых назван. Имена `ALL_SHOP_AD_SPEND` и `SHOP_AD_SPEND` MUST NOT выпускаться, пока охват всех кампаний магазина за окно не доказан. Это зависимость `BLOCKED_BY_SHOP_WIDE_CAMPAIGN_COVERAGE`. Текущий пакет может содержать только управляемый или инвентарный охват, а не весь магазин.

`SHOP_DRR` = весь рекламный расход магазина / вся фактическая выручка магазина. Число выпускается только когда доказаны оба знаменательных входа. Расход охвата пакета MUST NOT подставляться в `SHOP_DRR`. Выручка рекламной статистики тоже MUST NOT. Пока любого входа нет, метрика невычислима: одновременно `BLOCKED_BY_SHOP_WIDE_CAMPAIGN_COVERAGE`, `BLOCKED_BY_COMMON_SALES` и `BLOCKED_BY_SHOP_DRR_SOURCE`.

Заказы и сумма заказов кампанийной статистики публикуются только с областью `CAMPAIGN_WB_STAT`. Это не прямая и не связанная атрибуция. Воронка не подмешивается в эти поля и не становится выручкой магазина.

Прямые и связанные CPO/DRR имеют идентификаторы и формулы в контракте и статус «невычислимо», пока нет фактов атрибуции (`BLOCKED_BY_ATTRIBUTION_FACTS`). Тихого отката связанной метрики к прямой нет. Неизвестное покрытие атрибуции закрывается отказом, не оценкой. DRR магазина остаётся отдельным резервом и не выпускается числом на условиях абзаца выше.

Тождество для будущего режима, без реализации управления:

```text
Fact CPO = Spend / Orders
Fact DRR = Spend / GMV
Reference revenue per order = GMV / Orders
Target CPO = Fact CPO × Target DRR / Fact DRR
           = ReferenceRevenuePerOrder × TargetDRR
Max CPO = ReferenceRevenuePerOrder × MaxDRR
```

Считать это должен доменный код позже. Существующий фиксированный CPO не переинтерпретируется. `DRR_DYNAMIC` в этом change не включается.

### 3. Сравнения

Пары минимум: `1d` против `3d`, `3d` против `7d`, `7d` против `30d`, `30d` против `90d`, `90d` против `365d`, текущее календарное окно против того же календарного отрезка прошлого года, плюс уже существующие непересекающиеся предыдущие отрезки.

Статус пары:

- `COMPARABLE` — одна сущность, одна версия метрики, одна область атрибуции, оба окна покрыты полностью, знаменатели позволяют соотношение.
- `PARTIAL` — та же семантика, но хотя бы одно окно частичное или выборка ниже минимума, записанного в контракте.
- `NOT_COMPARABLE` — разное покрытие источника, неполный сегодняшний день, знаменатель ноль, разная область атрибуции, разная версия формулы, сущности не было в старом окне, источника нет.

Наличие двух чисел не делает пару сопоставимой.

Вложенные окна (`1d` внутри `7d`) сопоставимы как вложенные горизонты, не как независимые выборки. Контракт обязан это сказать.

### 4. Пропуски

Пропущенный день не становится нулём. Наблюдаемый ноль остаётся нулём. Неизвестное и нечисловое — пусто, не ноль. GAP семейства не порождает метрик этого семейства. Полнота одного семейства не делает пакет полным. Частичный сегодняшний день не называется полным днём.

### 5. Объём и производительность

Стратегия: вариант B — один доменный сервис. Экспорт (A) только вызывает его. Новая таблица (C) не создаётся, пока замер не покажет, что одного прохода по уже читаемой истории недостаточно.

Кампанийное зерно мало (ноги × дни). Его можно собрать одним проходом по дням и разложить по окнам в памяти. Ключевая история уже читается для существующего экспорта; второй полный скан ради нового слоя запрещён. Сервис потребляет уже посчитанные ключевые окна либо тот же однопроходный расчёт, не повторяя его.

Сырые факты остаются в пакете для точечного разбора. Инструкция запрещает грузить их в контекст целиком. В контекст по умолчанию входят сводка, покрытие, контракт, окна охвата пакета и ног, сравнения. Ключи и сырьё — только для отмеченных проблемных сущностей.

Поток JSONL, стабильный порядок, без глубокой вложенности. Сжатие ZIP не считается бюджетом токенов: несжатый ключевой JSONL может быть сотни мегабайт. Поэтому новые витрины держатся на крупном зерне.

Кэш границ окон — чистая функция водяного знака. Отдельный кэш агрегатов между экспортами не вводится.

### 6. Версии

| Объект | Старт | Ломающее изменение |
|---|---|---|
| `package_schema_version` | 1.1.0 для пакета с аналитическим слоем | Смена границ окон или формулы уже изданной метрики → мажор пакета и мажор контракта |
| `analysis_contract_version` | 1.0.0 | Новая метрика с новым id → минор. Смена формулы или окна → мажор |
| `metric_definition_version` | на каждый id | Обязателен в строке, где метрика посчитана |
| `ai_guide_version` | 1.0.0 | Текст инструкции может меняться минором и не меняет арифметику |

Пакет 1.0.0 без аналитического слоя остаётся валидным старым пакетом. Новый экспорт, который заявляет анализ, не имеет права остаться на 1.0.0.

### 7. Что проверяет код, а не только схема

JSON Schema проверяет форму. Доменный валидатор обязан отвергать: слияние ног, ноль вместо пропуска, откат связанной метрики к прямой, `coverage_status=COMPLETE` у окна только из-за `package_cutoff_date`, имя `latest_complete_date`, расход всего магазина без доказательства полного охвата кампаний, подстановку расхода пакета в DRR магазина, товарную строку без `KEYWORD_PERFORMANCE_PRODUCT_SCOPE`, намёк этой строки на всю выручку или DRR артикула, сравнение без статуса, окно `1d`, включающее дату сборки, дубль сырой строки по числу окон, расхождение версии формулы и значения.

## Risks / Trade-offs

- [UTC-день не доказан как отчётный день WB] → `package_cutoff_date` отдельно от `source_complete_through`; `source_period_closure` остаётся `UNKNOWN`.
- [Сумма пакета читается как весь магазин] → область `PACKAGE_CAMPAIGN_SCOPE`; `ALL_SHOP_AD_SPEND` закрыт охватом всех кампаний.
- [Артикул ключей читается как экономика SKU] → `KEYWORD_PERFORMANCE_PRODUCT_SCOPE` и отдельное имя файла.
- [Кампанийные заказы можно принять за атрибуцию] → отдельная область `CAMPAIGN_WB_STAT`, запрет имён DIRECT/LINKED.
- [Ключевой JSONL остаётся большим] → он не копируется; инструкция режет контекст.
- [Чтение campaign stat на 365 дней шире текущего CSV] → отдельное read-only чтение, без смены коллектора и без DDL.
- [Будущие экономические метрики] → идентификаторы зарезервированы, значения не выпускаются.

## Migration Plan

Аддитивные файлы и минор схемы пакета. Старые потребители 1.0.0 не обязаны читать анализ. Откат — не выпускать новые файлы и остаться на экспортёре без этого change. PR #450 не входит в миграцию.

Данных в БД этот change не мигрирует.

## Open Questions

Нет. Имена файлов и областей зафиксированы выше. Незакрытые источники классифицированы зависимостями, а не вопросами.

4. Посчитать витрины охвата пакета и физических ног без копирования сырья и без слияния Auto и Search. SOURCE: owner-contract, сумма ног пакета не есть расход всего магазина.
5. Пометить покрытие полного, частичного и пустого семейства на каждом окне. SOURCE: owner-contract и текущие GAP семейства.
6. Выпустить сравнения только со статусом сопоставимости. SOURCE: постановка сравнений в запросе Owner, перенесённая в owner-contract через «несколько горизонтов» и контракт метрик.
7. Отдать контракт и инструкцию транспорту. Экономические метрики без источника не выпускать. SOURCE: owner-contract, LLM не считает факты; прямая/связанная атрибуция и DRR магазина не выдаются без источника.
