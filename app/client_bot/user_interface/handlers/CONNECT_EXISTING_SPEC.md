# Подключение существующих РК (connect_existing_advs): целевое поведение

Документ фиксирует, **как должен работать** сценарий «Подключить существующие рекламные кампании» к артикулу (NM-id). Код обработчиков следует приводить к этому описанию.

**Обработчики:** [connect_existing_advs.py](connect_existing_advs.py)
**Для общей документации проекта:** рекомендуется скопировать/перенести в `docs/connect_existing_advs_flow.md`.

---

## 1. Модель данных

### 1.0 Как работает сейчас

- **Одна таблица AdvSetting** хранит всё подряд:
  - **«Главная» строка (комплекс):** одна запись на связку артикулов, где `adv_id` — ID авто-кампании на WB, `_search_adv_id` — ID поисковой. В этой же строке лежат общие настройки и поля авто (cpm, active_status и т.д.).
  - **Legacy-строки «только поиск»:** отдельные строки AdvSetting, у которых `adv_id` = ID поисковой кампании на WB (т.е. одна запись на одну поисковую РК). Они остались от старой логики «подгрузили все РК из WB и создали по строке на каждую».
- **На один артикул (набор nmids) может быть несколько строк AdvSetting:** одна «главная» (комплекс) и при наличии привязки — одна legacy «поисковая» (её `adv_id` совпадает с `_search_adv_id` главной).
- **Откуда берутся данные по поиску:** не из главной строки (там только `_search_adv_id`), а из legacy-строки. В `WBShopDataManager.get_complex_advs()` собираются все `search_adv_id` из активных AdvSetting, затем запросом по `adv_id in search_adv_ids` выбираются строки AdvSetting — это и есть legacy «только поиск». Они передаются в `ComplexAdv` как `search_adv`; из них читаются `cpm`, `active_status`, `adv_id`, `nmids` (см. п. 1.3). В `adv_setting_menu` при оценке свежести статы отдельно догружают строку по `AdvSetting.adv_id == self.adv.search_adv_id`.
- Итог: сущности «комплекс», «авто-РК» и «поисковая РК» в БД не разграничены — всё в одной таблице, различие только по смыслу полей и по тому, как код выбирает строки.

### 1.1 AdvSetting как ComplexAdv (текущая реализация)

- **AdvSetting описывает ComplexAdv:** связывает авто и поиск через `adv_id` и `_search_adv_id` соответственно.
- **Текущая реальность на WB:** создаём **две** РК на WB — одна несёт роль **комплексной + авто** (её ID хранится в `adv_id`), вторая — **привязанная к ней аукцион** (её ID в `_search_adv_id`). При создании поисковой на WB заполняем `_search_adv_id` в нашей записи. Логика сценария привязана к этой модели.
- Если по артикулу уже есть AdvSetting — её можно использовать для привязки новых кампаний (там уже есть настройки и т.д.).

### 1.2 Целевая модель (на будущее)

- **Одна AdvSetting на один артикул (или набор артикулов)** — целевое ограничение **на будущее**; сейчас возможно несколько записей (legacy).
- Все кампании появляются в боте **только** через сценарии **«Подключить существующие»** или **«Создать новые»**. В результате создаётся/обновляется запись AdvSetting с полями:
  - `adv_id: int | None` — ID **авто-кампании** на WB;
  - `_search_adv_id: int | None` — ID **поисковой (аукционной) кампании** на WB.
- На стороне WB кампании могут существовать или нет; пользователю всегда предлагается выбор: подключить существующую или создать новую.

**Инварианты целевой модели (на будущее):** (1) РК из WB в БД не подгружаются. (2) На один артикул (или набор артикулов) — ровно одна AdvSetting; создаётся только через подключение существующих или создание новых.

### 1.3 Legacy (как было и что остаётся в БД)

- **Изначально** из WB подгружались все РК, по ним создавались записи AdvSetting **без разбора**: и авто (type 9), и поиск (type 8). То есть на одну и ту же связку артикулов могло приходиться несколько строк AdvSetting.
- **Подход был такой:** «единой» оставляли **одну** AdvSetting, созданную на основе **авто-кампании** (в ней `adv_id` = ID авто-РК). К этой записи через поле `_search_adv_id` привязывали поисковую РК. Строка AdvSetting, созданная под **поисковую** кампанию (где `adv_id` хранит ID поисковой РК), при этом оставалась в БД как балласт.
- **Использование legacy «поисковой» строки в коде:** да, она **реально используется**, и не только как носитель ID. В `WBShopDataManager.get_complex_advs()` по всем `search_adv_id` строится маппинг `adv_id → AdvSetting` через `__get_adv_id_to_search_adv_map(search_adv_ids)` — выбираются строки с `adv_id in search_adv_ids`, т.е. legacy-строки «только поиск». Этот объект AdvSetting подставляется в `ComplexAdv` как `search_adv`. **Из него читаются поля:** `cpm` (ComplexAdv.search_cpm, _CPMs), `active_status` (search_adv_active_status_str, проверки на started в keyword_stamp_manager и др.), `adv_id` и `nmids` (минус-фразы, get_current_bids, minus_phrase_manager). В `adv_setting_menu` для оценки свежести статы явно догружают строку по `AdvSetting.adv_id == self.adv.search_adv_id` и передают в ComplexAdv. При переходе на одну запись на артикул: либо хранить данные по поиску (cpm, active_status) в основной строке или брать с WB API; маппинг по legacy-строке и передачу в ComplexAdv нужно убрать.
- Логика подключения должна различать: **комплексную запись** (одна строка, `adv_id` = авто, `_search_adv_id` = поиск); **legacy «только авто»** (одна строка, есть `adv_id`, нет `_search_adv_id`); **legacy «только поиск»** (одна строка, `adv_id` = ID поисковой РК). Нельзя трактовать любую найденную строку как пару `(auto_id, search_id)` без учёта типа записи.

### 1.4 Направление миграции (целевая схема БД, на будущее)

- **AdvSetting остаётся таблицей комплекса:** одна запись на один артикул (или набор артикулов). В ней хранятся только идентификаторы WB-кампаний (`adv_id`, `_search_adv_id`) и общие настройки комплекса (name, bot_active, strategy, nmids и т.д.). Поля, специфичные для авто или для поиска (cpm, active_status по каждой РК), из AdvSetting выносим.
- **Вводим отдельные таблицы для каждого вида РК:**
  - **Таблица под авто-РК** (например `adv_setting_auto`): `id`, `adv_setting_id` (FK на комплекс, связь 1:0..1), `wb_adv_id` (ID авто-кампании на WB), поля только для авто: `cpm`, `active_status`, при необходимости другие.
  - **Таблица под поисковую РК** (например `adv_setting_search`): `id`, `adv_setting_id` (FK на комплекс, связь 1:0..1), `wb_adv_id` (ID поисковой кампании на WB), поля только для поиска: `cpm`, `active_status`, при необходимости `nmids` и др.
- **Миграция:** данные из текущей «главной» строки AdvSetting (cpm, active_status по авто) переносим в строку `adv_setting_auto`, привязанную к этой AdvSetting. Данные из legacy-строки «только поиск» (где `adv_id` = search_adv_id главной) переносим в строку `adv_setting_search`, привязанную к той же главной AdvSetting. После переноса legacy-строки AdvSetting (отдельные по поиску) удаляем или помечаем как deprecated. Код переводим на сбор ComplexAdv из одной AdvSetting + опционально одной строки из `adv_setting_auto` + одной из `adv_setting_search`; маппинг `__get_adv_id_to_search_adv_map` и передачу второй строки AdvSetting как `search_adv` убираем.
- **На будущее (в миграции/схеме предусмотреть):** свойство (поле или отдельная сущность), которое **явно разделяет роли** — комплекс / авто / поиск — чтобы в коде и БД различать их однозначно. Сейчас одна WB-кампания совмещает роль комплексной и авто; явное разделение — в перспективе.
- В итоге сущности разграничены: **комплекс** — в AdvSetting, **настройки авто-кампании** — в своей таблице, **настройки поисковой кампании** — в своей.
- **На будущее:** в сценарии «Подключить существующие» должна появиться возможность подключить **только поисковую (ручную) РК без авто (единой)**. Сейчас сценарий всегда ведёт к паре (поиск + авто); в перспективе после выбора/создания поисковой пользователь должен иметь возможность завершить подключение без выбора авто (сохранение записи с `_search_adv_id` заполненным и `adv_id` пустым, с учётом новой схемы — запись в adv_setting_search при отсутствии adv_setting_auto).

## 2. Два источника данных

Поведение строится на **двух независимых источниках**:

| Источник | Вопрос | Использование |
|----------|--------|----------------|
| **БД (AdvSetting)** | Что уже подключено в боте для этого артикула? В каком формате (complex / legacy)? | Определить `connected_auto_id`, `connected_search_id`, не предлагать повторное подключение или создание того, что уже есть. |
| **WB (candidates)** | Какие кампании найдены на WB по артикулу и что можно предложить выбрать/создать? | Списки `auction_list`, `auto_list` для выбора «подтвердить существующую» или «создать новую». |

Итоговая ветка UI должна учитывать **оба** источника и не подменять один другим.

## 3. Нормализованное состояние по артикулу (после учёта БД и WB)

После получения кандидатов с WB и при необходимости синхронизации статусов из WB в БД, состояние по артикулу можно свести к одному из вариантов:

- **none** — в БД нет активной комплексной пары и нет подходящих legacy-записей по артикулу; на WB нет подходящих кандидатов (или списки пусты после фильтрации).
- **wb_auction_only** — на WB есть только поисковые кандидаты (auction_list не пуст, auto_list пуст).
- **wb_auto_only** — на WB есть только авто-кандидаты (auto_list не пуст, auction_list пуст).
- **wb_both** — на WB есть и поисковые, и авто-кандидаты.
- **db_pair_active** — в БД есть активная комплексная запись (или эквивалентная пара legacy): и авто, и поиск уже подключены.
- **db_partial_after_sync** — после синхронизации с WB в БД осталась частичная информация (только авто или только поиск), при этом списки кандидатов WB по какой-то причине пусты (both lists empty).

Поведение по веткам ниже описано так, чтобы не дублировать создание кампаний и не путать «есть в БД» с «есть в WB».

### 3.1 Поиск карточки по артикулу и fallback

При вводе артикула карточка сначала ищется по фильтру (textSearch). Если карточка по артикулу не найдена по фильтру, пользователю показывается сообщение с предложением выполнить поиск по полному списку; по нажатию «Загрузить и найти по полному списку» выполняется поиск без фильтра по батчам до нахождения одной карточки по nmID или до конца списка. Если и там карточка не найдена — показывается финальное «Артикул не найден» и кнопка «В меню магазина».

## 4. Целевые ветки после получения кандидатов

Ниже везде: `auction_list` / `auto_list` — списки кандидатов с WB (после фильтрации по статусу), уже сохранённые в FSM.

### 4.1 Уже есть полная пара в БД (до выбора кандидатов)

- **Условие:** `_get_existing_adv_pair_not_done` вернул пару `(auto_id, search_id)` с обоими значениями не None.
- **Действие:** Не входить в сценарий выбора кандидатов. Сообщить, что для артикула уже подключены РК (Аукцион и Авто), показать кнопку «В меню магазина».
- **Важно:** Это единственная ветка, где пользователю не предлагается ничего создавать или выбирать по этому артикулу.

### 4.2 Только авто без поиска (WB вернул авто, поисковых нет)

- **Условие:** `not auction_list and auto_list`.
- **Смысл:** На WB есть авто-кампании по артикулу, поисковых нет. Пользователь может создать поисковую на WB и привязать её; при наличии существующей AdvSetting по артикулу используем её для привязки (настройки и т.д. уже есть).
- **Действие:**
  - Перевести в состояние `waiting_confirm_continue_invalid`.
  - Показать текст про авто без поиска и кнопки: «Создать поисковую РК», «Отмена».
- Опция «Создать поисковую РК» не зависит от наличия записи с `_search_adv_id` в БД: наша запись в БД — сущность бота, она может существовать без живых кампаний на WB; при необходимости создаём поисковую на WB и заполняем/обновляем `_search_adv_id`.

### 4.3 Обе списки пусты (both lists empty)

- **Условие:** `not auction_list and not auto_list`.

Дальнейшее поведение зависит от того, есть ли в БД запись по артикулу до/после синхронизации с WB.

1. **В state есть `existing_auto_id` или `existing_auction_id`** (из ранее найденной пары/legacy):
   - Выполнить синхронизацию статусов из WB в БД по этим id (`_sync_adv_status_from_wb`).
   - Заново получить «пару» из БД: `existing_pair_after_sync = _get_existing_adv_pair_not_done(...)`.
   - Разветвить **по составу пары после sync**:
     - **Пара пуста (None):** сообщить, что кампания завершена/отсутствует, предложить «Создать обе (аукцион + авто)» → `waiting_confirm_create_both`.
     - **Есть и авто, и поиск:** не предлагать создание поиска. Сообщить, что обе РК уже есть, и предложить «В меню магазина» (аналогично п. 4.1).
     - **Только авто (есть auto_id, нет search_id):** предложить «Создать поисковую РК» (то же состояние/кнопки, что в п. 4.2), без перехода в ветку «создать обе».
     - **Только поиск (есть search_id, нет auto_id):** вести в сценарий выбора/создания **авто** (шаг 2), а не в создание поиска.

2. **В state нет ни existing_auto_id, ни existing_auction_id:**
   - Предложить «Кампании не найдены. Создать обе (аукцион + авто)?» → `waiting_confirm_create_both`.

**Критично:** В ветке «both lists empty» никогда не переводить пользователя в `waiting_confirm_continue_invalid` с кнопкой «Создать поисковую РК», если после sync в БД уже есть активная поисковая РК (`existing_auction_id_from_db` / search в паре). Иначе пользователь создаст дубликат поисковой кампании и перезапишет `_search_adv_id`.

### 4.4 Есть только поиск (в БД уже аукцион по артикулу)

- **Условие:** в данных после разбора кандидатов есть `existing_auction_id` (в БД уже есть поисковая по артикулу).
- **Действие:** Сразу перейти к шагу 2 (выбор/создание авто): установить `chosen_auction_adv_id=existing_auction_id`, состояние `confirm_type2`, показать **меню выбора способа** для авто (ввести ID / выбрать из списка / создать РК / назад) — см. п. 4.6.

### 4.5 Есть кандидаты обоих типов или только аукцион с WB

- Если есть `auction_list`: шаг 1 — выбор/создание поисковой (confirm_type1), затем шаг 2 — выбор/создание авто (confirm_type2).
- Если есть только `auto_list` — см. п. 4.2.
- При выборе «Подтвердить» по обоим типам — сохранение в AdvSetting одной комплексной записью (adv_id, _search_adv_id, nmids, и т.д.) или вызов задач create_auto_only / create_search_only при создании недостающей части.

### 4.6 Способы выбора РК на шагах 1 (аукцион) и 2 (авто)

На каждом шаге (поисковая РК и авто-РК) пользователю предлагается **меню выбора способа**:

1. **Ввести ID кампании** — пользователь вводит число (ID кампании на WB). Проверка: кампания должна существовать в WB, относиться к данному артикулу (nmid), быть нужного типа (аукцион или авто) и не быть в статусе «завершена»/«отклонена». При невалидном ID показывается сообщение об ошибке и кнопки «Ввести снова» и «Назад».
2. **Выбрать из существующих** — показываются все подходящие для артикула кампании данного типа (из `auction_candidates` / `auto_candidates`) кнопками; выбор одной завершает выбор по этому шагу.
3. **Создать РК** — постановка задачи на создание кампании (аукцион или авто) в очередь (если реализовано).
4. **Назад** — на шаге 1: выход в меню магазина; на шаге 2: возврат к меню выбора способа для аукционной РК (шаг 1).

Состояния FSM:

- **`confirm_type1` / `confirm_type2`** — меню выбора способа на шаге аукциона и авто соответственно (устанавливаются в `_send_auction_choice_menu` / `_send_auto_choice_menu`).
- **`waiting_auction_adv_id` / `waiting_auto_adv_id`** — ожидание **текстового** ввода ID после «Ввести ID кампании».

После действия **«Выбрать из существующих»** (`choose_list`) перед показом списка кампаний FSM переводится в `confirm_type1` или `confirm_type2` (режим выбора из списка).

Callback подтверждения выбора из списка (`ConnectExistingConfirmType1` / `ConnectExistingConfirmType2`) обрабатывается в состояниях **`confirm_type*` и `waiting_*_adv_id`**: это нужно, если пользователь сначала нажал «Ввести ID», а затем выбрал кампанию из **ранее показанного** списка в истории чата (несколько активных inline-клавиатур в Telegram).

Валидация введённого ID выполняется через WB API (`get_campaigns_info`) и классификацию по nmid/типу (как в `filter_and_classify_campaigns_by_nmid`).

## 5. Callback «Создать поисковую РК» (continue_despite_invalid)

- **Состояние:** `ConnectExistingAdvsStates.waiting_confirm_continue_invalid`.
- **Действие при confirm:** Поставить в очередь задачу `create_search_only` (nmid, shop_id, existing_auto_adv_id, user_telegram_id).
- **Обязательная проверка перед постановкой задачи:** Если в state есть `existing_auction_id` (поисковая РК по артикулу уже подключена в боте), **не** вызывать `create_search_only`. Сообщить пользователю, что поисковая РК уже существует, и завершить сценарий (например, очистить state и вернуть в меню магазина).
- Это защита от дублирования поисковой кампании и перезаписи `_search_adv_id` при ошибочном попадании в это состояние из ветки «both lists empty» (см. п. 4.3).

## 6. Backend (create_search_only)

- По смыслу: создание **новой** поисковой кампании на WB и привязка к существующей авто (одна комплексная запись AdvSetting с adv_id + _search_adv_id).
- Желательно (defence in depth): перед созданием проверять, что для данного nmid/shop_id ещё нет активной комплексной записи с заполненным _search_adv_id; при наличии — не создавать новую поисковую и не перезаписывать связь.

## 8. Связанные сущности

- **Типы РК (type):** 8 — поиск (аукцион), 9 — авто (и комплексная запись).
- **Статусы:** refused, done — не предлагаем для подключения; остальные (started, pause, ready_for_start и т.д.) — подходящие кандидаты после фильтрации.
- **extra_adv_ids:** ID из БД по артикулу передаются в `get_connect_existing_candidates`, чтобы WB вернул эти кампании даже при рассинхроне (например, по лимитам/фильтрам API).
