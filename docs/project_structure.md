# Структура телеграм-бота для управления рекламой на Wildberries

## Общая структура проекта

Проект представляет собой телеграм-бота для управления рекламными кампаниями на Wildberries. Бот позволяет пользователям добавлять магазины (кабинеты), управлять рекламными кампаниями, настраивать ключевые слова, контролировать ставки и многое другое.

### Основные компоненты проекта:

1. **app/** - основная директория с кодом бота
   - **client_bot/** - модуль клиентского бота
   - **modules/** - дополнительные модули функциональности (новая функциональность разрабатывается здесь)
   - **core/** - ядро проекта
   - **utils/** - утилиты и вспомогательные функции
   - **settings/** - настройки проекта
   - **directly_bot/** - модуль для непосредственного взаимодействия
   - **admin_bot/** - модуль административного бота
   - **predict_ctr/** - модуль для предсказания CTR

2. **migrations/** - файлы миграций БД
3. **alembic/** - конфигурация миграций
4. **tests/** - тесты проекта
5. **docs/** - документация
6. **scripts/** - вспомогательные скрипты

## База данных

Основные модели:
- **User** - пользователь системы
- **WBUserCabinet** - кабинет пользователя на WB
- **WBCabinet** - кабинет WB
  - Имеет гибридные свойства `calculated_balance` и `calculated_bonus`, которые суммируют значения из полей `balance` и `bonus` с записями из соответствующих платежных таблиц `WBBalancePayment` и `WBBonusPayment`
  - При работе с балансом и бонусами следует использовать эти гибридные свойства вместо прямых полей
- **WBToken** - токен API WB
- **AdvSetting** - настройки рекламной кампании
- **KeywordSetting** - настройки ключевых слов
- **WBBalancePayment** - записи о пополнении баланса кабинета
- **WBBonusPayment** - записи о начислении/списании бонусов кабинета

### Логика работы с балансом и бонусами

В системе реализована двойная система учета баланса и бонусов:
1. Прямые поля в таблице `WBCabinet`: `balance` и `bonus` - исторические значения
2. Таблицы транзакций: `WBBalancePayment` и `WBBonusPayment` - новые записи о пополнениях и списаниях

Гибридные свойства `calculated_balance` и `calculated_bonus` в модели `WBCabinet` объединяют эти два источника данных, 
суммируя исходное значение поля и все соответствующие транзакции. Это позволяет сохранить обратную совместимость 
с историческими данными и одновременно иметь подробную историю всех операций.

При работе с балансом и бонусами в коде:
1. Используйте гибридные свойства для получения текущих значений: `cabinet.calculated_balance`, `cabinet.calculated_bonus`
2. Для изменения баланса или бонусов добавляйте записи в соответствующие таблицы транзакций (`WBBalancePayment` или `WBBonusPayment`)
3. **Не модифицируйте напрямую** поля `balance` и `bonus` - это может привести к неконсистентности данных

## Как ориентироваться при модификации

### Добавление новой кнопки:
1. Создать новый callback в **app/client_bot/user_interface/views/callbacks.py**
2. Добавить кнопку в соответствующую клавиатуру в **app/client_bot/user_interface/views/keyboards.py**
3. Создать обработчик в нужном файле в **app/client_bot/user_interface/handlers/**

### Изменение интерфейса:
1. Интерфейсные сообщения находятся в **app/client_bot/user_interface/views/messages.py**
2. Клавиатуры - в **app/client_bot/user_interface/views/keyboards.py**

### Изменение логики обработки сообщений:
1. Найти соответствующий обработчик в **app/client_bot/user_interface/handlers/**
2. Внести необходимые изменения в логику

### Добавление нового функционала:
1. **Создать новый модуль** в директории **app/modules/**
2. Структурировать модуль согласно принятой архитектуре (handlers, models, service)
3. Создать роутер для модуля
4. Подключить модульный роутер в **app/client_bot/common_routers.py**

## Административные модули

### Принципы организации административных модулей

1. **Доступ к административным функциям**:
   - Административные функции должны быть доступны только пользователям из списка ADMINS
   - Модуль должен проверять права доступа через F.from_user.id.in_(ADMINS)
   - НЕ создавать отдельные команды для вызова административных функций

2. **Интеграция с пользовательским интерфейсом**:
   - Административные кнопки должны быть интегрированы в существующий пользовательский интерфейс
   - В обработчике основного меню проверять, является ли пользователь администратором, и добавлять соответствующие кнопки
   - Для перехода между меню использовать callbacks с соответствующими actions

3. **Структура административного модуля**:
   - Создать CallbackData класс в app/client_bot/user_interface/views/callbacks.py
   - Добавить функцию для создания клавиатуры в модуле
   - Экспортировать необходимые компоненты через __init__.py
   - Добавить обработчики для всех действий в файл handlers.py
   - Подключить роутер модуля в app/client_bot/common_routers.py

4. **Правильная организация для интеграции**:
   - В существующее меню добавлять админские кнопки в соответствующих хендлерах при проверке прав
   - Создавать callback-обработчики, а не команды
   - Для возврата в основное админ-меню использовать соответствующие callback

5. **Пример структуры модуля**:
   ```
   app/modules/module_name/
   ├── __init__.py              # Экспорт необходимых компонентов
   ├── handlers.py              # Обработчики запросов
   ├── service.py               # Бизнес-логика
   ├── keyboards.py             # Функции создания клавиатур
   └── repository.py            # Работа с БД (опционально)
   ```

## Система фильтров для админского доступа

Для обеспечения административного доступа к магазинам и рекламным кампаниям в системе реализованы специальные фильтры:

### AdminsGetShopFilter

`AdminsGetShopFilter` - специальный фильтр, который позволяет администраторам получать прямой доступ к магазину по его идентификатору (shop_id).

#### Особенности работы:
- Фильтр проверяет, что входящее сообщение содержит UUID в правильном формате
- Проверяет, что отправитель сообщения входит в список администраторов (`const.ADMINS`)
- При успешной проверке пользователь получает доступ к меню магазина через функцию `getting_shop_for_admin`

#### Интеграция с изоляцией сцен:
- Фильтр работает независимо от сцен, позволяя администраторам "перепрыгивать" между сценами
- При вызове `ShopMenu` администратор попадает в контекст магазина, минуя стандартные шаги выбора
- Идентификатор кабинета (wb_user_cabinet_original_id) сохраняется в FSM состоянии для обеспечения правильной навигации
- Такой подход обеспечивает изоляцию управления магазинами, позволяя администраторам работать параллельно с обычными пользовательскими сессиями

#### Связь с фильтрацией магазинов:
В системе также реализована возможность фильтрации магазинов на уровне конфигурации через параметр `SHOP_FILTER_LIST` в настройках. 
Это позволяет ограничивать список доступных магазинов для обработки в фоновых процессах.

#### Использование:
- Администратор отправляет UUID магазина напрямую в чат с ботом
- Фильтр `AdminsGetShopFilter` перехватывает это сообщение и выполняет проверки
- При успешной проверке вызывается функция `getting_shop_for_admin`
- Администратор получает доступ к ShopMenu с функциональностью управления магазином

### AdminsGetAdvByIdFilter

Аналогичным образом работает фильтр `AdminsGetAdvByIdFilter`, позволяющий администраторам получать прямой доступ к конкретной рекламной кампании по её ID.
