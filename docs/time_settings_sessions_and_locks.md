# Настройки времени показов: сессии и блокировки

## Проблема

В модуле настроек ограничений показов по времени (`app/client_bot/user_interface/handlers/time_settings/`) используются два in-memory хранилища:

- **`_SESSIONS`** — словарь сессий пользователей (ключ: `(user_id, adv_setting_id)`). В сессии хранится состояние диалога: экран, выбранные часы/дни, даты и т.д.
- **`_ADV_LOCKS`** — словарь `asyncio.Lock` по `adv_setting_id` для исключения одновременной записи в БД по одной кампании.

Оба хранятся только в памяти одного процесса бота.

### Когда это создаёт проблемы

1. **Рестарт процесса** — сессия теряется. Пользователь при нажатии кнопок в старом сообщении получает «Откройте актуальное меню» и теряет несохранённый черновик. Данные в БД не портятся.
2. **Несколько воркеров/реплик** — сессия в процессе A, callback в B → «Откройте актуальное меню»; `get_adv_lock` не защищает между процессами → гонки при записи в БД.

### Текущий режим

Polling и webhook по умолчанию — один процесс. При одном процессе критичной ошибки нет, только неудобство при рестарте.

---

## Варианты решений

### 1. Сессии в Redis

Ключи: `ts:msg:{user_id}:{message_id}` → session_id; `ts:session:{session_id}` → JSON сессии. TTL 24 ч. В `state.py` — чтение/запись в Redis вместо `_SESSIONS`.

### 2. Лок на запись в Redis (per adv)

Ключ `ts:lock:adv:{adv_setting_id}`, SET NX EX 30 перед записью в БД, release после. Паттерн как в `redis_lock_manager.py`. В `router.py` вместо `get_adv_lock` — Redis-лок.

---

## Порядок внедрения

1. Сначала сессии в Redis. 2. Затем Redis-лок при масштабировании вебхука.

Связанный код: `state.py`, `router.py` в `time_settings`.
